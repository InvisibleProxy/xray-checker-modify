# AGENTS.md

Правила для агентов и разработчиков, меняющих этот репозиторий.

## Общение

- Общайтесь с владельцем проекта по-русски, неформально и прямо.
- Не соглашайтесь автоматически: указывайте на риски и ошибки с доказательствами из кода или тестов.
- Не выдавайте предположение за подтверждённое поведение.

## Источники истины

При конфликте используйте порядок:

1. текущий код и успешно выполняющиеся тесты;
2. `PROJECT_CONTEXT.md` — архитектура, workflow и бизнес-правила форка;
3. `README.md` — эксплуатация и пользовательские сценарии;
4. `web/openapi.yaml` — публичный API-контракт;
5. `docs/` и upstream-документация — справочная информация.

Не копируйте подробные описания между документами. Обновляйте файл, которому принадлежит изменившийся аспект.

## Критические инварианты

- Реальный git root — текущий каталог `xray-checker`, а не внешний каталог `xray-chacker`.
- `StableID`, а не `Name`, является ключом статусов, speedtest, node archive, mute и персонального Test URL.
- Не нормализуйте и не переименовывайте имена из подписки без отдельного требования. Суффиксы Remnawave вроде `^~2~^` принадлежат источнику.
- При refresh сначала вызывайте `xray.PreserveStableIDs`, затем `xray.ValidateStableIDs` и только потом сравнивайте effective-конфигурации.
- Пустой или дублирующийся без учёта регистра `StableID` должен останавливать startup/refresh до создания StableID-keyed maps и restart Xray.
- Ручное и плановое обновление подписки должны использовать один workflow и не выполняться параллельно.
- Источники из `SUBSCRIPTION_URL` всегда запрашиваются с собственным `User-Agent: Xray-Checker` и фиксированным HWID checker-а: на этот заголовок опираются Subscription Response Rules панели владельца, а фиксированный HWID удерживает checker в одном слоте устройства. Профиль клиента задаётся только источнику, добавленному из панели, и никогда не становится глобальной настройкой.
- HWID источника генерируется один раз и не меняется при редактировании: удалённая панель привязывает к нему слот устройства, а новое значение отъедало бы новый слот до упора в лимит. Пустой HWID у профиля `checker` означает его фиксированное значение, а не отсутствие заголовка.
- Подписочный URL является токеном доступа: он не попадает в API, логи и backup. Admin API отдаёт только маску, `data/subscription_sources.json` исключён из резервной копии, а сохранение источника с пустым URL обязано сохранять прежний.
- Пустой refresh или удаление минимум трёх и не менее 50% прежних нод считается подозрительным: scheduled update блокируется, manual требует explicit force, привязанный fingerprint к previewed candidate; candidate Xray config не должен уничтожать last-known-good при неудачном startup.
- Ручной и плановый speedtest должны применять одинаковую логику URL: per-node URL имеет приоритет над глобальным. То же правило действует для per-node размера загрузки и per-node порога низкой скорости: отсутствие записи означает глобальное значение, ноль очищает переопределение, а сохранение расписания без этих карт обязано их сохранить.
- Порог низкой скорости выбирается по ноде через `LowSpeedThresholdFor` и решает fallback, confirmation retry и классификацию результата. Действовавший порог записывается в `Result.LowSpeedThresholdMbps`: все последующие читатели обязаны брать его оттуда, чтобы изменение глобальной настройки не переклассифицировало прошлые замеры. Ноль в поле означает отсутствие сохранённого порога и откат к текущему глобальному.
- Массовая корреляция считает знаменатель только по monitored-нодам: ноды в maintenance завышают порог 50% и подавляют инцидент, которого он должен был бы достичь.
- Отчёт speedtest показывает число фактически измеренных нод и отдельно число пропущенных (`RunReport.Skipped`); `Selected` переписывается фильтрами отчёта и не может служить этим числом.
- Любой писатель Telegram alert state, включая ручное обновление диагностики из бота, обязан держать `nodeNotifyMu`: смена статуса между рендером алерта и подтверждением его отправки не даёт сдвинуть reminder schedule и приводит к повторной отправке.
- Перед ручным speedtest из admin UI или Telegram сначала выполняется availability-check; в замер проходят только ноды с успешным proxy-check. Такой ручной запуск затем выполняет две фазы: сначала завершаются основные замеры, и только затем для low-speed или technical-error результатов запускается очередь country fallback. В history/report сохраняется один финальный результат на `StableID`.
- Плановый speedtest и automatic confirmation retry выбирают только ноды в effective-состоянии `online`; `proxy_failure` и `offline` не запускают замер и не создают speedtest history/result.
- Country fallback выбирается только по `ClaimedCountryCode` из node archive; GeoIP не участвует. Техническая ошибка либо скорость основного URL ниже текущего Telegram low-speed threshold переключает замер на fallback; нулевой threshold отключает переключение по скорости. Fallback не ниже threshold не создаёт автоматический Telegram report/alert. Медленный fallback и неразрешённый `context deadline exceeded` входят в общий 30-минутный confirmation retry, но причина результата не нормализуется: deadline сохраняется в `Error`/`PrimaryError` как технический timeout загрузки и не считается low-speed.
- Telegram-запуск speedtest использует сохранённый `ScheduleConfig`, а не нулевой `TestConfig`.
- Плановый speedtest сохраняет абсолютный `nextRunAt` в `speedtest_schedule.json`: restart и изменение фильтров/TestConfig/retention не должны начинать интервал заново. При изменении `IntervalSec` новый deadline считается от прежнего временного якоря; просроченный после downtime запуск выполняется один раз сразу, без серии catch-up запусков.
- Прямой результат Telegram-speedtest должен возвращаться в исходные chat ID и topic ID независимо от настроек фоновых speed-report; report target не персистится и не попадает в admin API.
- Первый фоновый low-speed результат (schedule/admin) сначала проверяется через country fallback и не уведомляет. Только если fallback тоже медленный либо доступные fallback URL завершаются ошибкой, просевшие `StableID` повторяются через 30 минут, а алерт отправляется лишь при повторной проблеме. Неразрешённый `context deadline exceeded` в `Error` или `PrimaryError` использует ту же очередь и те же правила подтверждения; fallback не ниже threshold закрывает событие без retry. Успешный ручной финальный результат до due time отменяет общий pending retry этой ноды; scheduled result чужой pending retry не отменяет.
- Pending speed-test retry персистится с нейтральным типом `speed-confirmation`, due time, исходным TestConfig и `StableID`, восстанавливается после restart и очищается для исчезнувших нод. Завершение confirmation-run очищает все запрошенные `StableID`, включая отфильтрованные или пропущенные без speed-result; не оставляйте persisted pending entry без активного timer. Legacy-записи без типа и с типом `low-speed` мигрируют без изменения due time; legacy `deadline` мигрирует в общую очередь, а её прежний 5-минутный due time сдвигается до 30 минут от исходного события. Все причины дедуплицируются по общему ключу `StableID`.
- Полный availability-check всех нод не использует TCP-гейт. Быстрый recovery-loop проверяет только уже недоступные `StableID`: обновляет TCP/ping и запускает proxy-check лишь после `TCP OK`; ping никогда не является gate.
- Availability имеет три состояния: `online`, `proxy_failure` и `offline`. При провале proxy-check сначала сохраняется `proxy_failure`; успешный TCP или ping не дают пометить ноду `offline`. Только одновременный провал proxy, TCP и ping открывает `DownSince` и node incident. `ProxyFailureSince`, cumulative duration/count и Telegram-состояние ведутся отдельно, без роста downtime. До завершения дополнительной TCP/ping-диагностики прежний `offline`/`DownSince` сохраняется. Для непривилегированного ICMP `udp4`/`udp6` не сопоставляйте reply по Echo ID: Linux может переписать его; используйте тип ответа, sequence и уникальный payload.
- Быстрые recovery-checks не увеличивают Telegram `FailCount` и не сдвигают reminder schedule. Подтверждённый online передаётся immediate-recovery пути без ожидания `AlertCheckMinutes`.
- Ручная availability-проверка из admin UI/API и карточки ноды Telegram использует общий workflow; для `online`/`unknown` выполняется полный proxy-check, для `proxy_failure`/`offline` — каскадная TCP/ping-проверка с proxy-check только после TCP OK.
- Maintenance mode хранится по `StableID` в node archive и исключает ноду из monitoring metrics/status, downtime/incidents, быстрого recovery-loop, планового speedtest и Telegram alert/retry. Медленный полный availability-loop продолжает probe-only proxy-check для Remnawave и не пишет его результат в monitoring statistics. Явный admin `Check`/`Run` остаётся разрешённым и не снимает maintenance; Telegram/manual non-admin paths paused-ноду пропускают. Ручной maintenance speed-result может быть виден в текущем admin snapshot, но не должен попадать в persisted latest/history, KPI, graph или Telegram. Включение режима закрывает текущий downtime и node incident, сохраняя cumulative downtime, incident journal, прежнюю speedtest history, mute и per-node Test URL; `/config/<StableID>` отвечает `200 Maintenance`, после `Resume` не выставляйте online без реального check. В Remnawave maintenance-нода остаётся member своей group: online probe ничего не меняет, подтверждённый offline обрабатывается обычно, а отдельный maintenance scenario разрешён только когда все members group одновременно offline и все находятся в maintenance. Неизвестный remote announce не трогайте.
- Project maintenance — отдельный глобальный режим в `data/project_state.json`, независимый от per-node maintenance: нода, поставленная на паузу до включения глобального режима, остаётся на паузе после выхода. Отсутствие файла означает выключенный режим. Переключение выполняется под Xray lifecycle write-lock, а проверка режима внутри `withCheckRun` стоит после взятия run-gate: начатый availability-check или speedtest досчитывается, новый не стартует. Приостанавливаются плановый availability-check и recovery-loop, плановый speedtest и confirmation retry, Telegram alerts/reminders/reports, автоматический subscription refresh и operational Remnawave reconcile/write. Продолжают работать Xray и пользовательский трафик, HTTP-сервер с `/health`, админка и API, автоматические backup, heartbeat diagnostic agents и явные admin `Check`/`Run`/backup/диагностика. Ручной speed-result во время режима помечается как probe и не попадает в persisted history, KPI и Telegram. Включение закрывает текущие downtime, proxy-failure и активные incidents, очищает Telegram alert counters и pending confirmation retries; история, cumulative downtime, настройки и mute сохраняются. `/config/<StableID>` отвечает `200 Project Maintenance` раньше per-node проверки, `/api/v1/status` возвращает `status: maintenance` и не подделывает ноды как offline. После `Resume` ноды остаются без статуса до реального check, а планировщик speedtest пересчитывает deadline от текущего момента и не выполняет серию catch-up запусков. Сам по себе режим ничего не публикует пользователям Remnawave.
- В admin UI действия `Check` и `Run` должны оставаться доступны одновременно в строке каждой ноды и в групповой панели выбранных нод. После клика `Run` UI сразу показывает локальное состояние `Starting…`, блокирует повторный запуск и после принятия backend-ом переходит к snapshot-состоянию `Running`; строковая индикация привязана к запрошенным `StableID`. Клик по этим кнопкам или checkbox не должен срабатывать как раскрытие строки; раскрывается только неинтерактивная область шапки либо отдельная стрелка. Master-checkbox в заголовке `Nodes` выбирает только текущие видимые `StableID` и обязан корректно отражать checked/indeterminate/disabled после фильтрации и изменения выбора.
- Повторный render admin dashboard при неизменном порядке видимых `StableID` должен обновлять карточки на месте, не заменяя весь список через `innerHTML`. Несколько карточек могут быть раскрыты одновременно; их history/range/request-state независимы, а polling и выбор строк не должны сбрасывать раскрытие или перезапускать графики.
- Ручной Pointer Events drag в `/admin` должен сохранять grab offset и двигать карточку 1:1, выбирать landing position по проекции release velocity и передавать эту скорость пружинному settle. Drag и раскрытие карточки обязаны быть прерываемыми с текущего экранного значения. Сохраняйте клавиатурные альтернативы, tab/tabpanel и `aria-sort`, системные reduced motion/transparency/contrast preferences и `rem`-масштабирование текста. Эти требования не распространяют визуальные изменения на публичный dashboard.
- Показанный IP/Server checker-ноды на dashboard и во всех admin views копируется кликом без порта; это интерактивное действие не должно раскрывать карточку или подменять отдельную ссылку IP details. Автообновление обязано запрашивать свежие данные и сопоставлять ноды по `StableID`, а не повторно рендерить старый snapshot или искать по имени.
- EN/RU-переключатель dashboard и admin UI использует общий ключ `xray-checker-language`; новые пользовательские строки и динамически создаваемые элементы должны иметь обе локализации. Не переводите operator-controlled значения и технические идентификаторы вроде `StableID`, `Test URL`, `Remnawave Host`, `Internal Squad`, `External Squad`, `announce` и `reconcile`.
- Speedtest удерживает Xray lifecycle read-lock от выбора нод до завершения теста; restart при refresh выполняется только под write-lock.
- Speedtest history хранится по возрасту; default 60 дней. Не возвращайте count-based limit.
- Availability latency history хранится в `node_registry.json` по `StableID` за тот же настраиваемый период, что и speedtest history: один sample на реальный `CheckedAt`, maintenance/probe-only checks исключены, уменьшение `HistoryRetentionDays` немедленно обрезает обе истории, а node merge переносит source history в active target с дедупликацией.
- Availability-график при наличии минимум 20 online samples использует адаптивный линейный scale до P90: значения выше верхней границы визуально прижимаются к ней и отмечаются peak-маркером, но реальные latency обязаны сохраняться в `Maximum`, tooltip и persisted history. При меньшем числе samples показывайте полный range; speedtest scale не меняйте.
- Переключение `Speedtest`/`Availability` в раскрытой карточке не должно менять координаты SVG-графика: блоки статистики обоих режимов обязаны резервировать одинаковую высоту, даже если `Measurements` или `Checks` переносится на вторую строку.
- График speedtest в admin UI строится только по сохранённым замерам Mbps и не интерполирует пропуски. Пунктирный gap bridge и error-зона являются только визуальными индикаторами отсутствующих результатов и не участвуют в статистике. Success percentage выбранного периода использует все history results как знаменатель; успешен только завершённый замер с Mbps не ниже low-speed threshold, а low-speed/offline/error считаются неуспешными. Диапазоны history API используют `from` включительно и `to` не включительно; обе границы передаются в RFC3339.
- Downtime в node archive накопительный и не должен очищаться вместе со speedtest history.
- GeoCheck выполняется только для active-нод. Retired StableID должен игнорироваться и при явном запросе через admin API. Оба geo-сервиса отвечают про адрес, поэтому DNS-имя ноды сначала резолвится: предпочитается IPv4, у имени с несколькими адресами берётся первый. Неудачный резолв фиксируется один раз для обоих сервисов и не порождает двух бессмысленных запросов.
- Dashboard KPI и список нод учитывают выбранную подписку. Переключатель над `Обзор` и фильтр `Subscription` в `Controls` обязаны читать одно значение, иначе сводка и список начнут описывать разные наборы нод.
- Incident journal хранит node и mass records; массовая корреляция требует одинакового failure code, минимум 3 и минимум 50% active scope. `check_endpoint` всегда маркируется как вероятностный вывод.
- Remnawave announce использует location-first mapping: `locations[locationKey].members` строится по `StableID → Host UUID`; имя checker-ноды и Host remark остаются только display-полями. Несколько StableID могут ссылаться на один Host, а redundancy нескольких Hosts задаётся составом members одной location. Audience filtering выполняется до агрегации location: одинаковые ключи разных тарифов не делают их Hosts резервами друг друга.
- Host не принадлежит External Squad напрямую. Audience определяется через Host inbound, membership inbound во внутреннем скваде, `internalSquads` хоста (`EXCLUDE` — deny-list, `ALLOW_ONLY` — allow-list; на панелях до 3.4 — устаревший `excludedInternalSquads` с семантикой `EXCLUDE`) и явную persisted пару Internal → External. Disabled/hidden Hosts исключаются; сервисная пара checker обязана быть `MonitoringOnly` и не может стать target.
- Новый Remnawave announce требует и минимального service-failure времени, и нескольких полных availability-итераций. Для announce `proxy_failure` и подтверждённый `offline` считаются недоступностью сервиса: таймер берёт `ProxyFailureSince` либо `DownSince`. Manual check и быстрый recovery-loop не увеличивают confirmation counter; probe-only full check maintenance-ноды увеличивает его. Active массовый `check_endpoint` не создаёт новый пользовательский announce. Location с healthy и подтверждённо offline members имеет partial-состояние; all-offline/all-maintenance location имеет maintenance-состояние; смесь maintenance и обычных offline members остаётся `down`. Full outage/maintenance имеют приоритет над partial. Улучшения `down/maintenance → partial/healthy` требуют отдельного стабильного окна и не публикуют специального recovery-сообщения.
- Remnawave write сначала перечитывает External Squads и case-insensitively merge-ит только `announce` в полной карте `responseHeadersAdd`. Существующий однострочный `rwEncodeBase64:` можно принять как opaque base: status добавляется через `\n`, а после очистки base восстанавливается байт-в-байт. Многострочное значение разрешено принять только при точном совпадении его suffix с rendered target/healthy message; preceding base сохраняется точно. Не принимайте под управление plain/многострочное неизвестное значение и не меняйте remote value, не совпадающее с persisted ownership state. Runtime v1/v2 мигрирует без получения новых прав на неизвестный remote header.
- Remnawave user messages строятся только из versioned scenario templates, а не строковых литералов в reconcile workflow. Разрешайте лишь контекстные `{location}`, `{locations}`, `{unavailable}`, `{affected}`, `{total}`; unknown braces, URL, `{{...}}`, line breaks и output длиннее 240 runes отклоняются. Disabled scenario очищает только exact-owned suffix. Config v0-v3 получает default rules, legacy `NormalMessage` мигрирует в healthy scenario; v1 API save без `messages`, v2 save без partial rules и v3 save без maintenance rules не должны сбрасывать сохранённые templates.
- Remnawave API token читается только из env и не попадает в persisted config, admin API, логи или backup. Минимальные scopes: `hosts:list`, `internal-squads:list`, `external-squads:list`, `external-squads:update`; последний scope всё равно даёт endpoint-wide write access.
- Failure code строится из proxy-check и прямых TCP/ping diagnostics; отсутствие ICMP reply не является самостоятельным доказательством offline.
- Remote Diagnostics остаются отдельной плоскостью: `diagnostics/` не импортирует operational packages и не получает callbacks, способные менять availability/nodearchive/incidents/Telegram/speedtest/Remnawave/subscription/backup. Observation хранится только внутри ephemeral session и никогда не становится authoritative status, history, KPI либо причиной operational side effect. Допустимо только read-only обогащение текста уже разрешённого локальными правилами Telegram-алерта вероятностной диагностической строкой; agent result не создаёт, не подавляет, не задерживает сверх настроенного bounded wait и не закрывает alert/retry.
- Diagnostic observation принимается только после проверки versioned schema, подписи, временного окна и точного binding по `SessionID`, `JobID`, nonce, `StableID`, generation, config fingerprint и server-owned profile ID. Execution proxy config, credentials, raw transport errors и произвольные URL не входят в session state/export.
- Логирование probe-agent идёт через опциональные hooks (`probeagent.Hooks`, `ExecutorConfig.OnDetail`), а не через package-level logger: тот же package линкует controller, и его log level не должен управлять агентским. Bounded-фраза и исходная ошибка передаются в hook раздельно — ошибка Xray или транспорта может процитировать фрагмент конфига ноды, поэтому binary печатает её только на debug. Token, приватные ключи, signing payload и сам Xray-конфиг в лог не попадают ни на каком уровне. Конфигурационные сбои по-прежнему уходят на wire единым bounded-кодом `configuration`; конкретный шаг живёт только в локальном логе.
- `PROBE_CONTROLLER_URL`/`PROBE_CONTROLLER_IP` — свойство controller-а, а не агента: они заполняют пустые поля create-запроса и префилят форму. Явное значение в запросе всегда побеждает default. Валидируются они той же `validateControllerAddress`, что и введённые вручную, и проверяются в `NewRegistry`, а не при первом `Create`. Задавать нужно оба или ни одного.
- Probe-agent предназначен для Linux и должен работать от отдельного непривилегированного пользователя. Не добавляйте в его lifecycle Windows-specific paths, service control или process semantics; временная Xray-конфигурация обязана удаляться после job.
- Probe-agent control client подключается только к exact `ControllerIP`, не использует environment proxy и не следует redirect; TLS ServerName берётся из HTTPS `ControllerURL`. Controller принимает enrollment/heartbeat только с exact `ExpectedSourceIP`. Forwarded source IP доверяется только при constant-time совпадении отдельного `PROBE_TRUSTED_PROXY_SECRET`, иначе используется socket peer.
- Heartbeat, job poll и observation submit используют общий persisted monotonic control sequence и identity-подпись, привязанную к method/path/body/timestamp. Credential-bearing single-node Xray config хранится только в ephemeral assignment queue, не входит в `DiagnosticSession`, export, logs или backup; job содержит только agent-owned fixed endpoint profile ID. Перед выполнением agent проверяет fingerprint и loopback-only SOCKS inbound, а перед приёмом observation controller повторно проверяет текущую generation/fingerprint.
- Enrollment token одноразовый и persisted только как SHA-256. После enrollment agent использует отдельную Ed25519 identity из persistent Linux volume; heartbeat sequence увеличивается и сохраняется до отправки, а controller сохраняет последний accepted sequence. Потеря identity volume требует явного Re-enroll, старый token повторно не действует.
- `diagnostic_agents.json` содержит controller/IP-bound security state и public identities, не входит в backup/restore. Admin list никогда не возвращает token/Compose; они доступны только в непосредственном create/reissue response. Удалять запись агента можно только после `Revoke`; `Delete` не управляет удалённым Compose stack или identity volume. Не логируйте token, private keys, proxy secret или signing payload с credential-bearing body.
- Sweep достижимости (`reachability/`) остаётся по ту же сторону границы, что и остальные remote observations: он читает `remoteprobe` через узкий интерфейс `SessionController` и не имеет пути к availability, incidents, speedtest, Telegram или Remnawave. Вердикт не выводится из observation без успешного direct-connectivity контроля и не выводится при локальном статусе `unknown`; находкой наблюдение становится только со второго совпадающего прохода подряд, потому что локальная половина сравнения отстаёт на величину до `PROXY_CHECK_INTERVAL`. Не заменяйте эту hysteresis на свежий локальный check: sweep не должен дёргать availability loop. Из сессии берётся одна ячейка, после чего сессия удаляется; в `data/reachability.json` не должно попадать ничего, кроме bounded classification values — причина `unknown` берётся из фиксированного списка фраз пакета, а не из текста ошибки. Ноды в maintenance и project maintenance sweep пропускает. Вердикт называет наблюдение (`agent_only_failure`, `local_only_failure`), а не причину, и не является operational state.
- `Connected` у агента — окно свежести (`max(3 × heartbeat interval, 90s)`), а не факт: его обновляют и heartbeat, и каждый job-poll. Любой отбор агента поэтому может попасть в уже ушедшего. Выполниться на нём job не может — доставка pull-based, — но может протухнуть, и потребитель обязан это переживать: sweep по timeout отменяет и удаляет session, не трогая прежнюю ячейку, а coordinator освобождает cooldown у session, завершившейся без observation. Не держите cooldown или иной блокирующий ресурс за session, которая ничего не принесла.
- `Retain` удаляет ячейки только исчезнувших и отозванных агентов. Агент, временно не на связи, сохраняет последнее наблюдение: оно единственная запись об этой точке. Такая ячейка помечается производным `Cell.Stale` и не участвует в `Alive`, `Unreachable`, `LocalUnreachable` и находках. Staleness выводится из `Cell.Generation` против текущего `sweepGeneration`, а не из сравнения времён: ячейки пишутся в течение прохода, поэтому отметка его завершения объявила бы устаревшими все. В UI устаревшая ячейка остаётся видимой, приглушается и показывает время последнего наблюдения; её подпись берётся из сохранённого вердикта, а не из производного `Unreachable`, которого у неё нет.
- Матрицу достижимости пишет только sweeper. Ручная диагностическая сессия в неё не попадает: она допускает любой профиль, разрешена на maintenance-нодах и остаётся read-only действием оператора. Точечная перепроверка — это `SweepNode`, тот же trigger и профиль, что и у планового прохода. Только полный проход выполняет `Retain` и двигает `MarkSweep`; single-node pass ничего не знает об остальных строках и удалил бы их.
- `Cell.Streak` считает независимые наблюдения: он растёт только когда `LocalCheckedAt` продвинулся с прошлой записи. Два наблюдения против одной и той же локальной выборки — одно свидетельство, прочитанное дважды, а `streak` существует ровно для того, чтобы пережить устаревший локальный результат. Не заменяйте это на «инкремент на каждую запись»: тогда повторный recheck подтвердит артефакт, который плановый проход отбросил бы.
- Находка достижимости определяется по строке, а не по паре. `Cell.Verdict` — это попарное сравнение с checker-ом и хранится как исторический факт; решение принимается по производному `Cell.Unreachable` и `NodeRow.LocalUnreachable`, которые вычисляются в `Rows()` и не сохраняются. Причина в том, что checker — такая же точка наблюдения: когда отрезан именно он, агент, который тоже не видит ноду, формально «согласен» с ним и его сообщение теряется, хотя другой агент доказал, что нода жива. Не считайте находки по `Verdict.Divergent()` и не считайте их в `sweepPair`: до конца прохода неизвестно, что видели остальные агенты. Нода, недоступная из всех точек, находкой не является. Checker даёт максимум одну находку на ноду, а не по одной на каждого агента, который до неё достучался.
- Активные ноды управляются подпиской; удалять вручную можно только retired-записи.
- Node merge разрешён только retired source → выбранный администратором active target после preview и совпадения нормализованных `SubName`, protocol и server. Name и port могут измениться, но preview обязан явно показать расхождения; confirmation token должен быть привязан к конкретному persisted candidate, а UI не должен выбирать target автоматически.
- Node merge применяется только на startup к `node_registry.json` и `speedtest_results.json`. До успешного `Load` speedtest, node archive и Telegram исходные файлы сохраняются для byte-for-byte rollback; incident ID не меняются, source StableID re-keyed, а lineage прежних ID не теряется.
- Node merge не переносит Remnawave location membership; после merge retired member заменяется оператором вручную на новый active `StableID` в нужной location. Не расширяйте merge-транзакцию на Remnawave config без отдельного дизайна rollback и проверки аудитории.
- Backup restore и node merge не должны одновременно находиться в pending/applied/rollback state; их web staging обязан удерживать общий transaction gate до публикации операции.
- Backup не должен включать environment, geo-файлы, `xray_config.json`, Telegram secrets/admin IDs, Remnawave API token и `remnawave_announce_state.json`. Versioned v5 `remnawave_announce_config.json` с non-secret policy/pairs/locations входит в typed backup; legacy node mappings мигрируют при чтении.
- `Caddyfile.example` является источником шаблона reverse proxy; локальный `Caddyfile` игнорируется и не должен попадать в коммиты.
- Закрытый Compose/Caddy-шаблон пропускает снаружи только `GET /metrics` с `BEDOLAGA_PUBLIC_IP` и четыре точных агентских `POST` endpoint. Остальные запросы, включая публичный API, получают `404`; порт checker-а публикуется только на host loopback. Сохраняйте `METRICS_PROTECTED=true`: Basic Auth метрик проверяет controller, Caddy не получает пароль. Не добавляйте общую Basic Auth поверх агентских маршрутов; сохраняйте их proxy-secret/source-IP headers.
- Автоматические backup: максимум один за UTC-день, максимум 7 файлов и максимум 7 суток.
- Restore всегда проходит типизированную JSON-валидацию и staging; применение — только на следующем startup с rollback. Commit допустим лишь после успешного `Load` у всех владельцев restored state.
- Restore transaction должна различать оборванное применение, неподтверждённое состояние и оборванную очистку подтверждённого commit; не удаляйте rollback-копию без commit marker.
- `/admin` и `/api/v1/admin/*` не должны становиться публичными.
- Server-mode не запускается с пустыми Basic Auth credentials; встроенные публичные credentials запрещены.
- Основной Telegram output использует Rich Messages и компактный HTML fallback. На неопределённой сетевой ошибке нельзя отправлять fallback повторно из-за риска дубля. `message is not modified` и rate limit не являются поводом для fallback: первое означает, что Rich-вариант уже на экране, и компактная правка молча заменила бы его.
- Перебор нод-кандидатов в Telegram-транспорте останавливается на первом полученном ответе Telegram: любой HTTP-ответ и `ok:false` окончательны для всех нод. Следующего кандидата пробуют только пока ответа нет либо тело не является ответом Bot API. Оборванное чтение уже отправленного запроса не повторяется ни через ту же, ни через другую ноду. `parameters.retry_after` уважается, `409 Conflict` логируется как второй потребитель `getUpdates`.
- HTTP-клиенты Telegram переиспользуются по SOCKS-порту, а срок запроса задаёт context вызывающего, а не `Client.Timeout`: long polling обязан иметь бюджет больше своего `timeout`-параметра.
- Обработка Telegram update обязана быть под `recover`, а запуск speed-test из бота — подтверждать callback до предшествующего availability-check и выполнять его в горутине под общим status-гейтом. Polling loop не должен блокироваться на время проверки.
- Telegram mute существует в двух формах с общим набором scope `all`/`alerts`/`speed`: временная тишина живёт в `node_alert_state.json` c `until`, не восстанавливается после истечения срока и удаляется вместе с исчезнувшей нодой; постоянная пишется в списки `telegram_config.json` и обязана оставаться видимой и снимаемой в админке. Постоянная тишина заменяет запущенный временный отсчёт, снятие убирает обе формы.
- Инлайн-клавиатуры со списками нод и замеров обязаны быть постраничными; запрошенная страница вне диапазона приводится к существующей. Текст экрана «Замеры» не постраничный: он группирует все ноды по `Ошибки`/`Низкая скорость`/`В норме`, сворачивая последнюю группу, а клавиатура обязана повторять этот же порядок, чтобы кнопки соответствовали прочитанному.
- `/id` отвечает до проверки чата и потому обязан быть ограничен по частоте на пользователя и глобально.
- Интерактивные Telegram-экраны «Проблемы» и «Замеры», кнопки speedtest history, текущая admin-таблица `Results` и dashboard KPI показывают только результаты active `StableID`; retired history остаётся в persisted state и доступна через архивные admin views.
- Recovery alert удаляется из persisted state только после успешной отправки соответствующего уведомления.
- `xray_config.json` — генерируемый runtime-файл, не источник истины и не часть backup.

## Правила изменений

- Перед правкой просмотрите `git status` и не затрагивайте несвязанные пользовательские изменения.
- Для поиска используйте `rg`/`rg --files`.
- Для редактирования файлов используйте patch, а не перезапись shell-хаками.

Карта лежит в package doc в `service.go`; добавляя код, кладите его в файл по смыслу и обновляйте карту, а не наращивайте один файл.
- Наследованные от upstream GitHub Actions и Dependabot отключены через `.gitignore`. Форк владеет только двумя собственными publish workflow — `probe-agent-image.yml` и `controller-image.yml`, каждый добавлен явным исключением в `.gitignore`. Не добавляйте другие workflow и `.github/dependabot.yml`; обязательные проверки выполняются локально перед push.

## Проверки

- Выполняйте только минимально необходимые проверки, достаточные для изменённого поведения и его ближайших зависимостей. Не запускайте полный набор тестов, `vet`, race-проверки или production build «на всякий случай».
- Форматируйте только изменённые Go-файлы. Для локального изменения начинайте с конкретных тестов через `go test ./package -run 'TestName1|TestName2' -count=1`; расширяйте запуск до всего затронутого package только когда точечных тестов недостаточно.
- Несколько package проверяйте только при сквозном изменении их контракта. `go test ./...`, полный `go vet ./...`, широкие `go test -race` и финальный Docker image нужны перед релизом/push либо когда масштаб или риск изменения действительно не покрываются узкими проверками.
- Если host Go отсутствует, используйте существующий Docker builder с тем же минимальным набором package/test names. Не пересобирайте production image, если изменение не затрагивает Dockerfile, Compose, сборку или релизный сценарий.
- В итоговом отчёте перечисляйте фактически выполненные проверки и отдельно отмечайте важные проверки, которые не запускались.

Дополнительные проверки по области: выбирайте из списка только сценарии, непосредственно затронутые текущим diff; это не обязательный запуск всего списка.

- subscription/identity: тесты `xray` и `nodemerge`, сценарии неоднозначных имён, stale confirmation, suspicious diff, interrupted apply/commit и rollback rejected candidate;
- speedtest: manual и scheduled paths, maintenance exclusion, per-node URL, retention и persistence;
